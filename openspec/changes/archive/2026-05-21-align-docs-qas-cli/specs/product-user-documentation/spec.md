## ADDED Requirements

### Requirement: Default product documentation describes QASpec core slash commands

Published product documentation under `docs/` SHALL describe the default installed agent surface as **`/qas:explore`**, **`/qas:analyze`**, **`/qas:matrix`**, **`/qas:publish`**, and **`/qas:archive`**, matching the `core` profile workflows installed by `qaspec init` and `qaspec update`.

#### Scenario: Getting started quick path

- **WHEN** a reader opens `docs/getting-started.md`
- **THEN** the primary workflow diagram or list SHALL use `/qas:*` commands for the default path
- **AND** SHALL NOT present `/opsx:propose` or `/opsx:apply` as the default next step after init

#### Scenario: Commands reference table

- **WHEN** a reader opens `docs/commands.md` quick reference
- **THEN** the default table SHALL list the five `/qas:*` core commands with purposes aligned to QA artifacts (`analisis.md`, `testmatrix.md`, publish, archive)
- **AND** legacy `/opsx:*` commands SHALL NOT appear in the default quick-reference table

### Requirement: Workflows documentation matches QA artifact pipeline

`docs/workflows.md` SHALL explain the QASpec QA pipeline (explore → analyze → matrix → publish → archive) and SHALL reference `qaspec instructions` and project `qaspec/references/` where applicable.

#### Scenario: Core profile section

- **WHEN** documentation describes the `core` profile
- **THEN** it SHALL enumerate exactly `explore`, `analyze`, `matrix`, `publish`, `archive`
- **AND** SHALL NOT state that `core` includes `propose`, `apply`, or `sync`

#### Scenario: Matrix and publish prerequisites

- **WHEN** documentation explains `/qas:matrix` or `/qas:publish`
- **THEN** it SHALL describe halts and prerequisites consistent with `qas-workflows-and-commands` (e.g. analyze before matrix, approval before publish)

### Requirement: Legacy OPSX documentation is explicitly secondary

Files that document `/opsx:*` or OpenSpec-style change scaffolding (`docs/opsx.md`, historical sections of `docs/migration-guide.md`) SHALL include a visible notice that QASpec CLI does not install those commands by default.

#### Scenario: OPSX dedicated page

- **WHEN** a reader opens `docs/opsx.md`
- **THEN** the page SHALL state that content is legacy/upstream context
- **AND** SHALL link to `docs/workflows.md` or `docs/getting-started.md` for the current QASpec default path

#### Scenario: Migration guide body

- **WHEN** `docs/migration-guide.md` references `/opsx:*`
- **THEN** those sections SHALL be framed as historical migration or upstream coexistence, not as commands generated by `qaspec init`

### Requirement: Supported tools documentation lists QASpec artifact paths

`docs/supported-tools.md` SHALL document installed paths for `qas-*` skills and `/qas:*` (or tool-equivalent) commands per supported AI tool, and SHALL NOT instruct users to run `qaspec config profile` to enable removed legacy workflow ids.

#### Scenario: Cursor paths

- **WHEN** documentation lists Cursor install paths after init
- **THEN** examples SHALL use `.cursor/skills/qas-analyze/` and `.cursor/commands/qas/analyze.md` (or current adapter paths)
- **AND** SHALL NOT list `openspec-apply-change` or `opsx-propose.md` as QASpec-generated defaults

### Requirement: Documentation regression guard for default slash commands

The repository SHALL include an automated test that fails when primary product doc files introduce `/opsx:` as default install guidance outside allowlisted legacy files.

#### Scenario: Primary docs scan

- **WHEN** CI runs the documentation guard test
- **THEN** files such as `docs/getting-started.md`, `docs/commands.md`, and `docs/workflows.md` SHALL be checked for unallowlisted `/opsx:` in default-path sections
- **AND** `docs/opsx.md` and `docs/migration-guide.md` MAY be excluded or allowlisted for historical `/opsx:` mentions

#### Scenario: Allowlisted legacy mention

- **WHEN** `docs/migration-guide.md` maps `/openspec:proposal` to `/opsx:propose` for migration
- **THEN** the guard SHALL allow that file without failing the build
